# GEMM 性能工程报告：#022 阶梯测速 + 手写 vs cuBLAS

- 平台：LeetGPU #022 General Matrix Multiplication (GEMM)，medium
- 语义：`C = alpha * (A × B) + beta * C_initial`，全 row-major，**fp16 输入 / fp32 累加 / fp16 输出**
- 题面性能规模：`M = N = K = 1024`（约束 `16 ≤ M,N,K ≤ 4096`）
- 本机：**RTX 5090 D（sm_120，170 SM，fp32 FFMA 理论峰值 104.8 TFLOPS @2.41 GHz）**
- 工具：`_tools/localrun.py`（NVRTC + Driver API）、`_tools/cublas.py`（cuBLAS 基线）、
  `_debug/_gemm_ladder.py`（fp16 阶梯）、`_debug/_gemm_sgemm.py`（fp32 阶梯）

---

## ⚠️ 先看这个：小规模测量不可信

ctypes 每次 `cuLaunchKernel` 有 **~7 µs 的 host 固定开销**（空 kernel 实测 6.7~7.3 µs）。
`timeit` 的计时环里如果 GPU 时间压不过 host 开销，**测到的就是 host 抖动，不是 GPU 时间**。

- `实测 / 7µs ≥ 4` → 可信；
- `< 4` → 数字被污染，**不能用来下结论**。

**在 1024³ 上，cuBLAS 的 fp16 只花 ~17 µs（比值 2.5×）→ 那一行根本测不准。**
所以 fp16 的横向比较一律以 **≥2048³** 为准；fp32 因为慢得多（46 µs+，比值 6.8×），1024³ 可信。

> 教训：中途曾"统一减去 7 µs"来做修正 —— **那是错的**。
> host < GPU 时流水线是满的，实测值**已经**就是 GPU 时间，再减会低估
> （会让 cuBLAS 的 fp16 数字虚高到 224 TFLOPS，超过硬件密集算力）。
> 正确做法是报告原始值 + 给出 host floor 让读者自行判断可信度。

## 三、fp16 三条结论

1. **「减少 `__syncthreads` 次数」比「加大瓦片」值钱**：BK 32→64 让 K=1024 的同步
   从 64 次降到 32 次，是本次最大的单项收益，且三种规模全胜 V5。改动只有一行宏。
2. **warp 级分块在 CUDA core 上有效但天花板低**：V6 把每 k 的共享读从 0.5 压到 0.375 次/FMA，
   +13.5%（相对 V1），但仍只有张量核路线的 **1/3** —— 瓶颈在 fp16→fp32 转换 + FFMA 吞吐，
   不在共享带宽（pad2 只值 +2% 早已证明）。
3. **瓦片不能盲目加大**：block 数必须 ≥ SM 数。128×64 → 128 block < 170 SM，V7 反而慢。

## 四、fp32 SGEMM：验证「tiling + reg + float4 + warp」

这一节回答一个具体质疑：**「在 T600 上 tiling+reg+float4+warp 能超过 cuBLAS」**。

前提修正：fp16 那张表里 cuBLAS 走**张量核**，CUDA core 手写实现永远追不上，
拿它证"手写打不过 cuBLAS"是**错的**。fp32 的 SGEMM 里 cuBLAS 也被限制在 **CUDA core 的 FFMA** 上，
双方同一起跑线。下面全部用 `CUBLAS_COMPUTE_32F`（**不是** TF32）。

### 1024³（比值 6.8× host floor，可信）

| 变体 | 耗时 | GFLOPS | % 峰值(104.8) | vs cuBLAS |
|---|---|---|---|---|
| cuBLAS SGEMM | 0.046 ms | 47 033 | 44.9% | 1.00× |
| F0 naive | 0.306 ms | 7 019 | 6.7% | 0.15× |
| F1 tiling+reg 64×64/4×4 **标量** | 0.062 ms | 34 526 | 33.0% | 0.73× |
| **F2 = F1 + float4 合并访存** | 0.058 ms | **37 155** | 35.5% | **0.79×** |
| F3 128×128/8×8 + float4 | 0.105 ms | 20 438 | 19.5% | 0.43× |
| F4 warp 分块 64×64/8×4 + float4 | 0.131 ms | 16 418 | 15.7% | 0.35× |

### 规模扫描 + 相对 cuBLAS

| 变体 | 1024³ | 2048³ | 4096³ | 比值 1024³ / 2048³ / 4096³ |
|---|---|---|---|---|
| cuBLAS SGEMM | 45 541 | 67 967 | 68 102 | 1.00× |
| F1 tiling+reg 标量 | 31 724 | 39 742 | 44 276 | 0.70× / 0.58× / 0.65× |
| F2 + float4 | 36 037 | 41 975 | 45 505 | 0.79× / 0.62× / 0.67× |
| F3 128×128/8×8 + float4 | 18 559 | 41 824 | 47 653 | 0.41× / 0.62× / 0.70× |
| F4 warp 分块 + float4 | 16 155 | 21 819 | 22 975 | 0.35× / 0.32× / 0.34× |

### fp32 结论

- ✅ **float4（合并访存 / 128-bit）确实有效**：F1 → F2 = 34 526 → 37 155 GFLOPS，
  **+7.6%**（1024³）。这条经验成立。
- ❌ **但「warp 分块」在 fp32 上是负收益**：F4 只有 0.32~0.35× cuBLAS。
  原因是 128 线程/block + 32 个累加器/线程 → 寄存器压力大、占用率低，
  且 warp 内 8 行之间跨 bank 回同一 bank（行距 20 words × 8 行）。
- **128×128 tile 在 1024³ 上差、在 4096³ 上反超**（0.41× → 0.70×）：又是 block 数问题
  （1024³ 只有 64 block，4096³ 有 1024 block）。
- **cuBLAS SGEMM 只跑到 FFMA 峰值的 45~65%** —— 旗舰卡上 cuBLAS 也没到顶，
  剩下的是 cp.async / 双缓冲 / swizzle 的工程量，不是调 tile 能补的。

## 五、为什么 T600 上能赢 cuBLAS（这台 5090 上不能）

**「手写能不能超过 cuBLAS」没有全局答案，它是
(GPU SM 数 × 矩阵尺寸 × dtype × cuBLAS 版本的启发式) 的函数。**

同一个 tile 在两台机器上的资源比完全不同：

| tile | 1024³ 的 block 数 | 40 SM（T600 / T4） | 170 SM（5090） |
|---|---|---|---|
| 128×128 | 64 | **1.6 waves —— 合适** | 0.38 waves —— 一半 SM 空转 |
| 64×64 | 256 | 6.4 waves —— 过载 | 1.5 waves —— 合适 |

- T600 是 **40 SM**，cuBLAS 在这种小卡上对**中等尺寸**的启发式容易选到非最优 kernel；
  而 128×128/8×8 + float4 恰好是匹配 40 SM 的经典配置 → **手写赢的窗口是真实存在的**。
- 5090 是 **170 SM**，cuBLAS 有更充裕的并行度和高度特化的 kernel，同一份手写代码就赢不了。
- 上一轮的结论「别指望手写追平 cuBLAS」**下得太绝对**：
  它只在「5090 + fp16 + 张量核」这个组合下成立，被错误外推到了 fp32 / 小 GPU。
  **T600 的结果和本机实测并不矛盾。**

## 五·五、v9：warp 三级分块实测（用户提供，2026-10-05）

设计：block 128×128、`blockDim=(4,64)`=256 线程、8 warp 排 2×4、每 warp 领 64×32、
线程在 warp 内排 8×4 → 微块 8×8，共享内存侧对 A/B 做 `float4` 读、C 做 `float4` 写。
`TS` = k 方向步长（决定 `__syncthreads` 次数 = 2K/TS）。

### ✅ 论点成立：比 reg8 快 7~26%

把 `TS`（k 步长，决定同步次数）和 `unroll`（k 循环展开度）做成**二维矩阵**扫了一遍 ——
因为两者是耦合的，只测"unroll 跟着 TS 全展开"会得出错误结论。1024³ 上（GFLOPS）：

| TS \ unroll | 全展开（=TS） | 8 | 4 |
|---|---|---|---|
| **8**（同步 256 次） | **20 479** | – | 17 622 |
| **16**（同步 128 次） | 17 155 | 19 755 | 19 675 |
| **32**（同步 64 次） | 16 112 | **20 491** | 19 024 |

| 变体 | 1024³ | 2048³ | 4096³ | vs cuBLAS 4096³ |
|---|---|---|---|---|
| cuBLAS SGEMM | 45 118 | 66 747 | 64 566 | 1.00× |
| F3 reg8 128×128/8×8 + float4（**v9 的对照组**） | 16 245 | 41 822 | 47 975 | 0.74× |
| **v9 TS8 全展开** | **20 479** | 48 765 | **51 298** | **0.79×** |
| ⭐ **v9 TS32 unroll8** | **20 491** | **50 182** | 50 975 | **0.79×** |
| v9 TS16 unroll8 | 19 755 | 47 176 | 48 910 | 0.76× |
| v9 TS32 unroll4 | 19 024 | 47 864 | 50 578 | 0.78× |
| v9 TS16 全展开 | 17 155 | 45 828 | 46 836 | 0.73× |
| v9 TS32 全展开 | 16 112 | 44 701 | 44 843 | 0.69× |
| v9 TS8 unroll4 | 17 622 | 41 354 | 44 699 | 0.69× |

- 相对 reg8：**1024³ +26% ／ 2048³ +20% ／ 4096³ +6.9%**。
- 1024³ 也拉开了差距（早先一次测出"持平"是 1% 级噪声）。

### ⚠️ 三个必须知道的点

1. **`APAD` 必须是 4 的倍数（原文的隐患，会直接崩）**
   原文对共享内存做 `float4` 读：`*reinterpret_cast<const float4*>(&As[k][aBase])`，
   而行距是 `WBM + APAD = 128 + APAD`。若按经典做法取 `APAD=1`（pad 一个 float 消
   bank conflict），**奇数 `k` 的行首只落在 4 字节边界上 → `float4` 读未对齐 →
   `CUDA misaligned address` 崩**。本次实测只能取 `APAD=4` 才跑得起来。
   → 一旦把共享读向量化，就**不能再用奇数 padding**，这是"向量化"与"消冲突"的硬冲突。

2. ⭐ **别让 `#pragma unroll` 跟着 `TS` 走 —— 把展开度钉住，TS 就能自由加大**
   二维表的规律非常干净：**最优展开度几乎与 TS 无关，都是 ~8 次**。
   - TS=8：全展开（=8）最好，降到 unroll 4 反而掉 14%；
   - TS=16：unroll 8/4 都行，全展开（=16）掉 12%；
   - TS=32：unroll 8 最好，全展开（=32）掉 **21%**。

   原因：展开体大小 ≈ `unroll × (4 个 float4 载入 + 64 FMA)`，
   **寄存器压力只由 unroll 决定，与 TS 无关**；而同步次数只由 TS 决定。两者解耦之后
   就能同时吃到红利 —— 这就是 **TS32+unroll8** 能追平并反超 TS8 的原因
   （2048³：50 182 vs 48 765，+2.9%）。

   → **修正「BK 32→64 值 +35%」那条规则的适用范围**：它成立的前提是
   *k 循环本来就没被全展开*（WMMA 的 BK 只改 fragment 级循环次数，不增大展开体）。
   对 **CUDA core 手写**的实现，正确姿势不是"别加 TS"，而是
   **「把 unroll 钉在 8 左右，然后放心加 TS」**。

3. **「地址数减少」≠「bank 冲突消除」（理论口径要修正）**
   v9 把 warp 内地址数从 36 降到 24（-33%）这一步是**真的**，
   但 `tyw * 8` 这个 float 偏移让 8 个 `tyw` 组的首地址在 bank 上按
   `0,8,16,24,0,8,16,24` 循环 → **8 线程组内仍有 2 路冲突**，
   而且靠 padding 改不掉（8 的步长本身才是元凶）。
   所以 v9 拿到的收益主要来自 **更少的 load 指令数 + 更多广播命中**，
   而不是冲突被彻底消除。想真正消掉，得上 swizzle / `ldmatrix` 那一类布局。



## 五·六、v10：移植 siboehm kernel10（warptiling）到 v9 上，2026-10-05

把 `refs/SGEMM_CUDA/src/kernels/10_kernel_warptiling.cuh`（A6000 上 **93.7% cuBLAS**）
的设计移植过来。与 v9 的结构差异：

| 项 | 用户 v9 | siboehm K10 |
|---|---|---|
| block / 线程 | 128×128 / 256 | 128×128 / **128**（4 warp） |
| warp tile | 64×32 | **64×64** |
| 线程微块 | 8×8（64 acc） | 8×4 + **WNITER** 子块分列（128 acc） |
| 共享载入/FMA | 16/64 = 0.25 | 24/128 = **0.1875** |
| **padding** | `APAD=4`（**必须 4 的倍数**） | **完全不需要**（A 转置存 `As[k*BM+row]`，行距 = BM 恰为 4 的倍数） |

实测（5 次取稳定值；fp32 方阵，无 alpha/beta）：

| 变体 | 1024³ | 2048³ | 4096³ | vs cuBLAS 4096³ |
|---|---|---|---|---|
| cuBLAS SGEMM | 43 500~47 200 | 67 500~68 000 | 65 000~68 500 | 1.00× |
| v9 TS8 全展开（旧最好） | 20 300 | 48 800 | 53 850 | 0.79× |
| v9 TS32 unroll8 | 20 400 | 50 400 | 53 000 | 0.78× |
| v10 = K10 原样（4 warp，标量共享读） | 18 000 | 46 400 | 48 000 | 0.70× |
| v10b = v10 + **float4 共享读** | 18 350 | 48 500 | 49 800 | 0.73× |
| v10c = v10b + **BK 16→32** | 20 100 | 50 950 | 54 000 | 0.79× |
| ⭐ **v10d = 8 warp / 半宽 warp tile（64×32, WNITER=2, NT=256）** | **23 780** | **53 300** | **58 700** | **0.86×** |

### 结论

- ✅ **移植成功，跑出新的最好成绩**：4096³ 从 v9 的 0.79× 提到 **0.86×（+9%）**；
  1024³ 从 20 300 提到 **23 780（+17%）**。
- ⚠️ **但 siboehm 的原始配置（v10）在这张卡上是最差的** —— 0.70×，比 v9 还低。
  **他的参数是为 A6000（84 SM）调的，不是为 5090（170 SM）调的。**
- **可归因的增益**：
  - v10 → v10b：**float4 共享读 +4.5%**（共享读指令数减半）；
  - v10b → v10c：**BK 16→32 +11%**（`__syncthreads` 减半，与 fp16 那边的结论同向）；
  - v10c → v10d：**+9%**，把 4 warp/128 线程换成 8 warp/256 线程。⭐ 机理明确：
    **1024³ 下 128×128 tile 只有 64 个 block，而卡有 170 个 SM —— block 数 < SM 数，
    每个 SM 只分到 1 个 block，于是 `NT` 直接决定了占用率**，256 线程正好是 128 的两倍。
    （所以"block 数 ≥ SM 数"这条规则的**补救办法**是：block 数不够时，加大每个 block 的线程数。）
- **不能归因的部分**：v10d 相对 v9 的差距**不是共享载入次数造成的** ——
  两者都是 16 次/64 FMA = 0.25（v10d 的 NT=256/半宽 warp tile 恰好抵消了 WNITER 的收益）。
  真正的来源是 NT=256 的占用率 + BK=16 的同步减半 + FMA 嵌套顺序，要精确归因得上 Nsight Compute。
- 顺带验证：**siboehm 的 As 读同样存在 2 路 bank 冲突**（`threadRowInWarp*8` 步长），
  他照样 93.7% ⇒ **bank 冲突不是瓶颈**这条再次成立。
- ✅ **他的"无 padding"布局是个真收获**：A 转置存 `As[k*BM+row]`，行距 = BM（4 的倍数）
  → float4 读天然 16B 对齐，**彻底绕开 v9 那个「APAD 必须是 4 的倍数」的硬约束**。

### 参数空间扫描：v10d 是局部最优（每条轴 3 次重复）

以 v10d 为基准，沿三条轴各推一格（BM=BN=128 固定）：

| 变体 | 1024³ | 2048³ | 4096³ | vs cuBLAS 4096³ | 结论 |
|---|---|---|---|---|---|
| cuBLAS SGEMM | ~45 500 | ~67 600 | ~67 900 | 1.00× | – |
| ⭐ **v10d**（NT=256, WM=64, WN=32, WNITER=2, BK=16） | **23 780** | **53 400** | **57 700** | **0.85×** | **基准，最优** |
| v10e = v10d 但 **BK 16→32** | 22 000 | 51 000 | 53 800 | 0.79× | ❌ 负收益 |
| v10g = **NT 256→512**（warp tile 降到 32×32） | 22 200 | 45 700 | 47 000 | 0.69× | ❌ 明显变差 |
| v10h = warp tile 换朝向（WM=32, WN=64, TN=8） | 22 300 | 50 400 | 53 400 | 0.79× | ❌ 略差 |
| v10c（NT=128, 64×64, WNITER=4，载入/FMA=0.1875） | 20 100 | 51 000 | 51 000 | 0.75× | 输给 v10d |

**三条轴都推不动 —— v10d 是当前设计空间的局部最优。** 具体读法：

1. **「BK 加倍」不是普适的**：在 v10b→v10c 上是 +11%（49 800 → 51 000），
   但在 v10d 形状上换成 **-7%**（57 700 → 53 800）。⇒ BK 的最优值依赖 shape/占用率，
   不能当成"越大越好"的万能旋钮。
2. **占用率有上限**：NT 256→512 **明显变差**（-18%）。原因有两层：
   acc/线程 从 64 掉到 32 → ILP 不足；共享载入/FMA 从 0.25 恶化到 0.375。
   ⇒ 「block 数不够就加 NT」这条**只在 NT ≤ 256 这一档成立**，翻过头就伤。
3. **⭐ 载入/FMA 比值不是这里的杠杆**：v10c 已经做到 **0.1875**（比 v10d 的 0.25 低 25%），
   但它输给 v10d（51 000 vs 57 700）。**所以剩下那 15% 的差距不在共享带宽上。**
4. **warp tile 的朝向（M 拉长 vs N 拉长）影响很小**（±5%，接近噪声）。

⇒ **参数微调到头了。** 剩下的 0.85× → 1.00× 需要**结构性**的改变，
唯一还没试的大杠杆是 **`cp.async` 双缓冲**（让 k 循环的 global→shared 载入与 FMA 重叠）——
参考实现就在 `refs/cuda_hgemm/src/wmma/wmma_async_pg2s*.cu`。



## 六、对 LeetGPU 榜单的意义（重要）

- 榜单接口 `GET /api/v1/challenges/<id>/leaderboard?language=cuda&accelerator=<acc>`，
  **每张卡只返回前 3 名**，按 `executionTime` 升序；无全局总榜（`/api/v1/leaderboard` 404）。
- **设成 public 只是必要条件，不是充分条件** —— 2026-10-05 实测：53 个成功提交全部设为

## 八、cuBLAS 基线怎么接（可复用到其他矩阵题）

`leetgpu-work/_tools/cublas.py`（ctypes 直调 `cublas64_12.dll`）。四个坑：

1. **cuBLAS 是列主序**：row-major 的 `C = alpha·A·B + beta·C` 要**交换 A/B 且交换 m/n**：

   ```
   cublasGemmEx(h, OP_N, OP_N,
                m=N, n=M, k=K,
                alpha, B, CUDA_R_16F, N,   // 实参 A' = B（列主序 N×K）
                       A, CUDA_R_16F, K,   // 实参 B' = A（列主序 K×M）
                beta,  C, CUDA_R_16F, N,
                CUBLAS_COMPUTE_32F, CUBLAS_GEMM_DEFAULT)
   ```

   原理：行主序 M×N 那段内存按列主序读就是 N×M（= 转置），
   `C^T = B^T A^T` 与原式共享内存布局，**不需要真的转置**。
2. **handle 必须在 CUDA context 已 current 之后创建**（先 `Runner`，再 `cublas.Handle()`）。
3. 走 NULL stream，与 `cuLaunchKernel(hStream=None)` 同一条流，计时可直接横比。
4. `gemm_f32` 用 `CUBLAS_COMPUTE_32F`（**别用 FAST_TF32**），才是与 CUDA core 手写同赛道的比法。
