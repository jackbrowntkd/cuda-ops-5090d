# 5090D CUDA 算子优化系列

在 **RTX 5090 D（sm_120，170 SM）** 上，用「厂商库基线 → 差距量化 → 抄开源实现的结构 →
参数扫描与归因 → 平台榜单」的闭环，逐个算子做性能对标与优化。

不是"跑通就跑"的 kernel 集合，而是**每一步都有可量的数字、可复现的命令、以及明确标注的
"哪些结论依赖机器规模"**。

---

## 一、先立两个天花板

优化之前必须先知道天花板在哪，否则不知道还差多少。

| 天花板 | 本机实测 | 对标哪类算子 |
|---|---|---|
| **D2D 显存带宽** | **1 514.9 GB/s** | 纯 elementwise / 数据搬运（= 理论上限） |
| **cuBLAS fp32 FFMA** | ~63~68 TFLOPS | 计算密集型（fp32） |

> ⚠️ **「5090 的 fp32 = 116 TFLOPS」是 TF32 张量核，不是真 FFMA。**
> 真 fp32（PyTorch 默认不开 tf32 实测 66.4 / 本机 `CUBLAS_COMPUTE_32F` 实测 68）≈ **66~68 TFLOPS**。
> 这个区分很关键 —— 报"和 cuBLAS 的比值"时不说清路径，数字就是错的。
>
> 本机带宽实测与第三方 [`binbinsh/gpu-bench`](https://github.com/binbinsh/gpu-bench) 的
> 1 528.8 GB/s 只差 **0.9%**，交叉验证通过。

## 二、差距总表（**本仓库的核心产出**）

规模全部取自各题题面写明的**性能测试规模**，不是自己另选。
下表的"优化后"是 2026-10-05 用本仓库的方法论做的一轮实战结果。

| 算子 | 厂商库 | 优化前 | 优化后 | 提升 | **差距**（题面规模） |
|---|---|---|---|---|---|
| fp16 GEMM（1024³） | 124 437 | 27 300 | **82 000** | 3.0× | 0.59× → **0.66×** |
| fp32 GEMM（8192×6144×4096） | 61 222 | 5 876 | **44 146** | **7.5×** | 0.09× → **0.72×** |
| fp32 batched（256³×128） | 39 924 | 5 929 | **46 176** | **7.8×** | 0.15× → **1.16×** |
| fp16 batched（256³×128） | 98 030 | 6 242 | **115 367** | **18.5×** | 0.07× → **1.18×** |
| int8 MatMul（8192×4096×2048） | 210 704 ⚠️ | 6 463 | **86 678** | **13.4×** | 0.03× → **0.41×** |

单位均为 GFLOPS（fp16 与 int8 为各自 dtype 的吞吐）。

⚠️ **int8 那行不是严格可比**：cuBLAS 侧是纯 int8 GEMM（int32 累加），**不含
zero_point / scale 校正**，只能当"忽略零点校正的理论上界"。
我们的 `solution_032_dp4a.cu` 是**完整**实现（含零点校正），所以 0.41× 是偏保守的读数。

### ⚠️ 但是：单形状的结论站不住 —— 扫 10 个形状后要修正

上表的数字都是**题面那一个规模**上的。换个形状结论会变 —— 所以本仓库加了多形状扫描
（[`common/sweep_shapes.py`](common/sweep_shapes.py)），覆盖"单个小矩阵 → 多个大矩阵"整个区间：

| 家族 | 题面那一点 | **10 个形状的几何平均** | 赢的形状数 | 最差 / 最好 |
|---|---|---|---|---|
| fp32 batched | 1.16× | **0.874×** | 5 / 10 | 0.40× / 1.22× |
| fp16 batched | 1.18× | **0.907×** | 3 / 10 | 0.73× / 1.20× |
| fp32 单发 GEMM | 0.72× | **0.600×** | **0 / 7** | 0.37× / 0.90× |

> **"两题反超 cuBLAS"这个说法只在题面规模上成立，不能当结论用。**
> 站得住的表述是：**在 batch 足够大（总 block 数 ≥ ~4×SM）或矩阵小到厂商库
> 启发式失准时能赢；一旦回到小 batch / 中等规模，就掉到 0.4~0.7×。**

### 四条结论

1. **fp16 GEMM 达到厂商库的 0.75×（题面规模），fp32 GEMM 0.72%。** 完整阶梯见
   [`docs/GEMM-PERF.md`](docs/GEMM-PERF.md)：从 naive 6 950 GFLOPS 一路到 v10d 的
   57 700（4096³），每一步的增益都是分开量的。
2. ✅ **已修：tile 尺寸自适应 + guard 编译期化 —— fp32 GEMM 几何平均 0.584x -> 0.836x**

   **问题**：固定 128x128 tile 喂不满 170 个 SM。

   | 形状 | 128 tile 的 block 数 | 修复前 | 修复后 |
   |---|---|---|---|
   | 512³ 单发 | 16 个 | 0.51x | **1.34x** |
   | 1024³ 单发 | 64 个 | 0.37x | **0.77x** |
   | 4096³ 单发 | 1024 个 | 0.69x | **0.84x** |
   | 题面 8192x6144x4096 | 2048 个 | 0.71x | **0.87x** |
   | **几何平均** | | **0.584x** | **0.836x（+43%）** |

   **两个正交的修法**：

   a) **tile 分档**：判据是「128 tile 的 block 数能否 >= SM 数」——
      能就用 128 tile（数据复用率高），不能就换 32 tile（block 数 x16）。
      交叉点实测就在 SM 数附近，不需要精调阈值。

   b) ⚠️ **边界 guard 做成编译期开关**。受控实验（同一模块/同一 grid/同一数据）：

      | kernel | 512³ | 1024³ |
      |---|---|---|
      | 无 guard | **13 592** | **35 958** |
      | 逐元素 guard + 标量回退 | **4 805** | **17 274** |

      **逐元素 `if (r < M)` 的代价是 2.8 倍** —— 它让编译器无法把 float4 载入
      当成无条件操作来调度，在 32 线程的小 block 上尤其致命。
      改成 `template <..., bool GUARD>` 后对齐形状零代价。

   实现：4 个实例化 = {128,32} tile x {无 guard 快路径, 带 guard 安全路径}，
   solve() 两条判据分派。⚠️ 快路径**只能**喂对齐形状（拿 M2N2K2 测会 misaligned address），
   所以 check.py 里快路径按对齐条件过滤、安全路径在所有形状上验。

   **剩余短板**：窄长形状（512x4096x4096，M 只有 512 行）仍只有 16 个 block，
   需要 **split-K**（沿收缩维切分再归约）—— 本方法论还没覆盖这一档。
3. ⭐ **小尺寸 batched 确实是厂商库的弱区**：256³×128 时 cuBLAS 只有 39.9（fp32）/
   98.0（fp16）TFLOPS，而同类的**大尺寸单发**是 61.2 / 212.6 TFLOPS
   （fp16 只保留了 **46%**）。但要注意 —— **这个窗口比单形状结论暗示的窄得多**。
3·5. ⭐ **BK（k 步长）必须实测扫，不能外推。** fp16 GEMM 的 `BK 32→64` 有 +25%，
   但继续往上调**不是单调的**：实测 BK=64 是 71 560、**96 是 82 000（+15%，最优）**、
   80 崩到 49 969（-30%）、128 崩到 44 320（-40%）。
   （80 崩的原因未定；128 大概是共享内存 ≈53KB 压低占用率。96 的占用 ≈44KB。）

3·6. ❌ **cp.async 双缓冲在这台卡上被否了**（实测更差 20~23%）。动机是粗算 4096³
   的搬运 ≈4.2GB、按 L2 带宽折合 ≈1.05ms ≈ 实测总耗时 0.97ms，以为重叠能接近 2×。
   实测 1024³ 74 088→59 362（0.80×）。**根因：双缓冲把共享内存 44KB 翻到 71KB，
   占用率 2 block/SM → 1。** 而 **5090 的 L2 有 96MB、A+B 只有 67MB ⇒ 数据本来
   就在 L2 里**，延迟隐藏本来就不缺，重叠的收益抵不过占用率损失。
   ⇒ **判据：先算 `数据量/L2`，远大于 1（真 DRAM 受限）时 cp.async 才值得**。
   （另：这个场景估算搬运算必须用 **L2 带宽**，我一开始按 DRAM 估，才把结论判反。）

4. **int8 用 `__dp4a` 拿到 13.4× 提升**。关键在于那个代数恒等式 ——
   `(A-zA)` 可达 ±255、**塞不进 int8 硬件路径**，必须把零点校正挪到 epilogue：

   ```
   Σ(A-zA)(B-zB) = ΣAB - zA·ΣB - zB·ΣA + K·zA·zB
                   ^^^^   ^^^^^   ^^^^^   ^^^^^^^^
                   纯int8   列和    行和     常数
   ```

   全程整数运算，**结果与原式逐位相同**（不是近似）。

## 二·五、把自适应分档推广到 batched（2026-10-05）

| 家族 | 优化前几何平均 | 优化后 | 赢的形状数 |
|---|---|---|---|
| fp32 batched (#030) | 0.874x | **1.133x** | 5/10 -> **9/10** |
| fp16 batched (#057) | 0.907x | **0.902x** | 3/10 -> 4/10 |

- ✅ **#030 提升 +30%**，256³ B=1 从 0.40x 到 1.65x。
  关键：batched 的判据**必须把 batch 乘进 block 数** —— 256³ 单发只有 4 个 block 喂不满，
  但 256³ B=128 就是 512 个 block，够用。
- ⚠️ **#057 基本没变**，而且试出一个**反例**：给大规模加一档 128x128 WMMA tile
  反而更差（512³B32 0.56x vs t64 的 1.20x、1024³B16 0.65x vs 0.86x）。
  原因：128 tile 只能配 BK=32（共享内存吃紧），而 **BK=64 才是 #022 上的最大单项收益**
  （K 方向 __syncthreads 减半，+35%）。**tile 放大但 k 步长变小 ⇒ 净效果为负。**
  ⇒ 已回退，只保留 t64/t32 两档。

## 二·六、归约 / 扫描族（基线是"带宽下限"，不是 cuBLAS）

归约只读不写（输出 1 个数），理论上限 = 读入字节 / D2D 带宽。

| 题 | 规模 | 达标率 |
|---|---|---|
| #027 MSE | N=5e7（读两个数组 400MB） | **96.2%** |
| #047 Subarray-Sum | N=1e8（读一个数组 400MB） | **86.1%** |

⇒ **#027 已贴天花板**；#047 还有 14% 空间（与它的 stage1 只开 1024 个 block 有关）。

## 二·七、第二轮：修窄长形状（split-K）+ 归约族优化

### ✅ 窄长形状已修：fp32 GEMM 几何平均 0.845x -> **0.874x**，最差 0.51x -> **0.66x**

第一轮在这个形状上试"换非方形 tile"失败了（结果算错）。第二轮换了**正确**的思路：
**split-K** —— 把收缩维 N 切段，每段一个 block，用 `atomicAdd` 累加到同一片 C。

为什么这次对：窄长形状的 128x128 tile **数据复用率是好的**（0.0156），只是
block 数不够（512x4096x4096 只有 128 个）。切 K 能在**不牺牲复用率**的前提下
把 block 数乘上去 —— 而换小 tile 虽然 block 数够，复用率却差 8 倍。

| 形状 | 原来 | split-K | 比值 |
|---|---|---|---|
| 512x4096x4096 | 0.51x | **0.64x** | +25% |
| 1024x4096x4096 | — | 0.66x | |
| 256x4096x4096 | — | 0.72x | |

⚠️ 代价：必须先 `cudaMemsetAsync` 清零 C（atomicAdd 会累加到垃圾值上），
已在计时里计入。正确性 rel=1.3e-06 ✓

### ✅ #047 Subarray-Sum：86.1% -> **97.7%**（带宽达标率）

| 改动 | 效果 |
|---|---|
| stage1 改 **int4 向量化**载入 | 86.1% -> 93.2% |
| grid 上限 1024 -> **4096** | 93.2% -> **97.7%** |

⚠️ **反直觉**：grid 并不是越大越好 —— cap=32768 掉到 86.8%、cap=65535 掉到 80.6%。
因为 stage2 要把所有部分和再归约一遍，block 越多、末段串行开销越大。**最优在 4096。**

## 二·七·五、norm 族：单遍读 vs 两遍读取决于「一行的数据量」

| 题 | 一组/一行多大 | 达标率 | 能否用「单遍读」 |
|---|---|---|---|
| **#083 Fused-Residual-Add+RMSNorm** | C 个元素（C=4096 → 16KB） | 71.7% → **99.9%** | ✅ 放得进 shared |
| **#113 LayerNorm** | C 个元素（C=512 → **2KB**） | **94.5~97.5%（本来就好）** | 不用改，第二遍天然命中缓存 |
| **#105 GroupNorm** | (C/G)·H·W（→ **256KB**） | 35~56% → **64.7%** | ❌ 放不下，两遍读是固有代价（上限 66.7%）|

⭐ **同族不等于同问题 —— 必须看具体的数据尺度。**

**#105 的三处改动**（都在 pass 2）：
1. ⚠️ **去掉逐元素的 64 位变量除法** —— v1 的 `c_local = (int)(i / HW)`（`i`/`HW` 都是 long long）
   在 cnt=262144 时每线程要算 **1024 次**。改成「外层遍历通道、内层遍历 HW」即可消除。
2. gamma/beta 提到循环外（同通道内是常量）
3. 两趟都改 float4

结果（最干净读数 N=16 C=512 H=128 W=128，数据量/L2=10.7）：**49.4% → 64.7%**，
已接近 66.7% 的理论上限。

### ⚠️ 方法论：静态启发式筛选不可靠
用「循环里有无除法 / 有无 float4 / 是否两趟读」静态扫 33 道待提交题，
**30 道被标成候选** —— 包括实测已 94.5% 的 #113 和实测 150% 的 #106。
⇒ **启发式只能排优先级，判断必须靠实测**（带宽达标率 + 数据量/L2 ≥ 4 + 实测/host ≥ 4）。

## 二·八、仍没成功的（诚实记录）

1. **#057 的 128x128 tile 是负收益**：128 tile 只能配 BK=32，而 BK=64 才是这条线的
   最大单项收益（+35%）。tile 放大但 k 步长变小 ⇒ 净负。已回退。
2. **#057 的 t32 档收益不稳定**（256³B=1 在 0.69~0.88 之间跳），小规模测量噪声大。
3. **#032 int8 上张量核本轮没做（诚实说明）**

   先扫了 dp4a 版本的 tile 配置，确认**它已经局部最优**，没有便宜的出路：

   | (TM, TN) | 每 k 组的 共享读/dp4a | GFLOPS |
   |---|---|---|
   | **4, 4（当前）** | 0.50 | **89 439** |
   | 8, 4 | 0.375 | 78 701 |
   | 4, 8 | 0.375 | 79 673 |
   | 8, 8 | 0.25 | 61 449 |

   ⇒ 加大寄存器分块反而更差（acc 要 64 个 int32，寄存器压力上去、占用率下来）。

   要真正追上 cuBLAS 的 210 TFLOPS 必须上 `mma.sync.m16n8k32.s8`，这需要
   **手写 A/B fragment 的元素→(row,col) 映射**（A 每线程 4 个 .b32 寄存器、
   B 2 个、C 4 个 s32），没有 reference 可以逐位核对，出错风险高。
   本轮没能在可靠正确性门禁下完成，**按要求不发布未验证的 kernel**。

   > 注：这里**不是**精度问题 —— `s32` 累加器是逐位精确的。
   > （精确性约束只对 fp16 张量核成立：fp32 累加器在大 K 下会越过 2^24 的精确整数范围。）

## 四、方法论（六步闭环）

1. **确认架构**：sm_120 走的是 Ampere 那代的 `mma.sync`（warp 级、寄存器到寄存器），
   **不是** SM100 的 `tcgen05`、**也不是** SM90 的 `wgmma`。
   → DeepGEMM / CUTLASS SM100 collective / WGMMA 版 flash-attention **在 5090 上编不过或崩**。
   能用的是 WMMA、`mma.sync` PTX、`cp.async`。
2. **量厂商基线**：每个算子都有基线。计算密集 → cuBLAS/cuDNN/CUB；
   **纯 elementwise → D2D 带宽即上限**。
3. **量化差距**：见下面的测量纪律。
4. **抄参考的结构**：⚠️ **抄结构，别抄参数** —— 把别处调好的 tile/线程数直接搬过来会翻车
   （见 `docs/GEMM-PERF.md` 里的 v10 vs v10d）。
5. **参数扫描 + 归因**：一次动一两个维度、每格重复 3 次取中位数、
   **把"可归因"和"不可归因"分开写**。
6. **提交与榜单**：榜单每张卡只返回前 3 名；`isPublic=true` 只是必要条件，进前 3 才上榜。

### ⚠️ 测量纪律（不遵守就会得出错结论）

- **host launch floor**：ctypes 每次 `cuLaunchKernel` 有 **~7 µs** 固定开销。
  `实测 / 7µs ≥ 4` 才可信；否则测到的是 host 抖动。
  → fp16 GEMM 在 1024³ 上 cuBLAS 只要 17 µs（比值 2.5×）→ **那一行根本测不准**，
  横向比较一律以 ≥2048³ 为准。
- **不要"统一减去 7 µs"**：host < GPU 时实测值**已经**是 GPU 时间，再减会低估
  （会让 cuBLAS 的 fp16 虚高到 224 TFLOPS，超过硬件密集算力）。
  正确做法是**报告原始值 + 标注可信度**。
- **单次测量不可信**：同一个 kernel 有一次跑出 27 029 GFLOPS，其余 5 次都是 55 600~59 200。
  **改结论前重复 3~5 次。**

## 五、复现

依赖：CUDA Toolkit（本仓库用 v12.8 的 `nvrtc64_120_0.dll` + `cublas64_12.dll`）、Python + numpy。
**不需要 nvcc** —— 全部 kernel 走 NVRTC 编译。

```bash
cd common
python vendor_baseline.py          # 带宽上限 + GEMM 家族厂商基线
python vendor_baseline.py bw       # 只量带宽
python bench_ours_vs_vendor.py     # 逐题差距

cd ../gemm-fp32 && python ladder_fp32.py     # fp32 十一级阶梯
cd ../gemm-fp16 && python ladder_fp16.py     # fp16 十二变体
```

> 注：原开发环境的 `nvcc` 不可用（`cl.exe` 会调用被安全策略拦截的 `reg.exe`），
> 所以整套测试框架走 `NVRTC + CUDA Driver API`（纯 ctypes，零编译工具链依赖）。
> 这个取舍也意味着**本仓库可以在没有完整 CUDA 工具链的 Windows 机器上复现**。
